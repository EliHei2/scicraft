# Review, packaging, sharing

Status: in the original build the review and packaging steps were planned in the state file and had
not yet run when this skill was last revised. The order and the checks come from that plan and from
the author's practice in earlier work; their yield is not recorded here.

## Coverage first, then review

Run the coverage audit, the reconciliation and the gap-fill agents (SKILL.md section 10,
`references/build-and-review.md`) before the review, so reviewers read the skills as they will ship.

## Adversarial review

- **One fresh reviewer per skill**, an agent that never saw the brief or the findings. It reads the
  skill as a researcher from another field and attempts one realistic task with it. Every place it
  stumbles is fixed, not explained away (the author's practice for newcomer audits of releases).
- **Lenses that matter for a distilled skill**: evidence (does each rule carry a number, command or
  reason?), generality (would it work in another field?), privacy (anything a terms file missed:
  a dataset described too exactly, a number from unpublished work), integrity (any rule that reads
  as hiding results), voice (machine-made prose), and links and scripts (run them).
- **Reviewers report; one agent applies** per skill, then re-runs the gate and the scripts it touched.
  The finder, verifier and edit-protocol mechanics belong to `adversarial-audit`.
- **Read the flagship SKILL.md files yourself**, end to end.
- **Check unpublished content once more**: method details and benchmark numbers of work not yet
  public. Incident numbers from debugging may stay.

## Packaging

- `README.md` (what the package is, how to install, the plugins and their skills), `THIRD_PARTY.md`,
  a license file, an index of skills generated by a script.
- **Install test in an isolated configuration folder**, so the user's own skills and settings are
  neither used nor touched by the test.
- Plugin validation with the agent tool's own validator.
- Never edit the user's own configuration folder or personal skills during the build; the package
  lives in its own folder.

## Where to ship (as of late 2026)

Options found in the official documentation on the day of the original build; verify them again,
they change:

| Option | Who can install | Notes |
|---|---|---|
| public git repository as a plugin marketplace | anyone | no usage numbers reach the author; updates when users update |
| private git repository | anyone who can clone it | access through the user's own git credentials |
| project settings that enable the marketplace | everyone who opens that repository | each user accepts once per clone |
| managed settings of an organization | every machine under the policy | admin-controlled; organization analytics |
| organization sharing on the web app (Team or Enterprise) | organization members | organization analytics |
| official plugin directory | anyone | needs a public repository, a README of at least 40 words and a license; the listing belongs to the organization that submits it; the author gets a private usage tab |

- **Ownership comes first.** Work done on an institution's time and subscription may belong to the
  institution. Ask before publishing; settle the license; decide whose account submits a listing,
  since the listing belongs to the submitter.
- A pattern that fits a researcher who moves labs: the public core and field plugins under an open
  license in the author's own repository, with a citation file and a DOI, after the institution signs
  off; the internal plugin in the institution's own git host; the receiving labs install from the
  public repository or mirror it. Suggested, not yet tested in real work.

## Portfolio numbers

If the author wants numbers for a portfolio:

- **Scale**, by script: prompts and projects from the digest index, findings words, rules, procedures
  and failures from `tally_findings.py --totals`, and skills, reference files, scripts and eval cases
  from a stats script over the package.
- **Effect**: the agent tool's plugin evaluation can run each eval case with and without the plugin
  and report the difference, with options for runs, model, judge model and a cost cap. Run it on a
  subset first; it costs real money.
- **Adoption** after release: only where the channel reports it (organization analytics, the
  directory's usage tab). A public repository reports nothing.
